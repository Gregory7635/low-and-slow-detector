# Этап 3. Реализация

## 3.1. Организация разработки

- **Методология:** список задач по этапам (Kanban-доска из колонок
  «требования → проектирование → ядро → ML → API/UI → тесты → документация»).
- **Git:** ветки `main` (стабильные версии) ← `develop` (интеграция) ←
  `feature/*` (по одной на этап: `feature/docs`, `feature/core`,
  `feature/ml`, `feature/api`, `feature/tests`, `feature/report-docs`,
  `feature/model-comparison`, `feature/storage`, `feature/uml`).
  Ветки сливаются через `merge --no-ff`, чтобы история этапов была видна.
- **Инструменты:** Python 3.11, pip (`requirements.txt`), pytest, ruff (PEP 8),
  GitHub Actions (линтер и тесты на каждый push).

## 3.3. Ключевые компоненты

### Разбор журнала

Регулярное выражение разбирает строку формата combined; время
переводится в UTC вручную, без `strptime`, IP
нормализуются через `ipaddress`. Нераспознанные строки не роняют
программу, а считаются в статистике.

### Правила

Правила оформлены как стратегии с общим интерфейсом:

```python
class Rule(ABC):
    id: int
    name: str

    def prepare(self, ctx):        # глобальная подготовка (DNS, окна подсетей)
        ...

    @abstractmethod
    def check(self, ip, records, ctx):   # подробности или None
        ...
```

`RuleEngine` сначала вызывает `prepare` у всех правил (правило 1
готовится первым: подтверждённые поисковики исключаются из остальных
правил), затем `check` для каждого IP.

В прототипе проверки User-Agent 3h–3m стояли после `return` и не
выполнялись (а ещё ссылались на неопределённые константы). При переносе
в модуль это исправлено, недостающие таблицы добавлены. Проверку 3i
(Chrome на Android без «Android 10; K») на реальном журнале давала 229
ложных срабатываний из-за встроенных браузеров приложений, поэтому она
помечена как слабая: попадает в отчёт, но сама правило не включает.

### Признаки

Для каждого IP с числом запросов ≥ 5 считается 21 признак (`features.py`):
интенсивность, регулярность (CV, энтропия интервалов, доля самого
длинного перерыва), состав запросов (статика, ошибки, POST, параметры),
Referer, разнообразие путей и User-Agent, размер подсети в журнале.
Счётчики логарифмируются, затем `StandardScaler`, значения обрезаются
до ±8σ.

### ML-компонент

**Разметка.** Настоящей разметки нет, поэтому `simulate.py` внедряет в
реальный журнал 516 ботов четырёх типов (`timer`, `random_slow`,
`distributed`, `mimic`). Пути и User-Agent берутся из того же журнала,
IP — из зарезервированного для тестов диапазона 198.18.0.0/15.

**Обучение.** Модели без учителя обучаются только на «чистых» реальных
IP train-выборки (не синтетические и без срабатывания надёжных правил).
Порог подбирается на validation по максимуму F1 и сохраняется вместе с
моделью. `precision_recall_curve` считает положительными оценки ≥ порога,
а детектор сравнивает строго, поэтому порог ставится посередине между
оценкой граничного IP и ближайшей меньшей.

**Автоэнкодер** (`models/autoencoder.py`):

```
21 → 16 → 8 → 3 → 8 → 16 → 21        ReLU
Adam (lr = 1e-3, weight_decay = 1e-5), MSE, batch 128,
до 300 эпох, ранняя остановка (patience = 25)
```

Архитектура выбрана перебором 18 вариантов по F1 на validation
(`scripts/experiments.py`, результаты — в 04_testing.md, 4.2).

Оценка аномальности — средняя ошибка восстановления; ошибка по каждому
признаку объясняет, чем IP отличается от нормы (`top_features` в отчёте).

**Isolation Forest:** 300 деревьев, `max_samples="auto"`, оценка
`-score_samples`.

**Сохранение:** `AnomalyDetector.save()` — joblib со scaler, порогом,
списком признаков и состоянием модели (для PyTorch — `state_dict`).
`AnomalyDetector.load()` + `predict()` / `score()` / `explain()`.

**Итоговое решение** (`pipeline.py`): IP — бот, если сработало надёжное
правило (1, 3, 5, 6) или оценка модели-«решателя» (по умолчанию
автоэнкодер) выше порога. Правило 2 — слабый сигнал, только в отчёт.

### REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | состояние, версия, загруженные модели |
| GET | `/api/models` | пороги и признаки моделей |
| POST | `/api/analyze` | загрузить журнал (multipart), параметры — в query |
| GET | `/api/analyses` | история анализов (новые первыми) |
| GET | `/api/analyses/{id}` | результат анализа (`only_bots=true` — только боты) |
| DELETE | `/api/analyses/{id}` | удалить анализ вместе с решениями по IP |
| GET | `/api/analyses/{id}/download` | JSON с ботами для выгрузки |
| GET | `/api/ips/{ip}` | решения по одному IP во всех анализах |

Параметры проверяются Pydantic (`AnalyzeParams`), модели и соединение с БД
создаются один раз (`lru_cache`). Документация Swagger — `/docs`.

### Хранение истории

`AnalysisRepository` (`api/storage.py`) — слой доступа к данным поверх
`sqlite3`: `save`, `get`, `list`, `ip_history`, `delete`. Схема создаётся
из `api/schema.sql` при первом подключении. Запись анализа и всех его IP
выполняется в одной транзакции, удаление каскадное (`ON DELETE CASCADE`).
Соединение защищено блокировкой (обработчики FastAPI работают в пуле
потоков), режим WAL и тайм-аут 30 с позволяют запускать несколько
процессов uvicorn.

Файл кэша DNS общий для всех запросов, поэтому под блокировкой только его
чтение и запись: перед сохранением кэш перечитывается, и новые записи
дописываются к результатам других запросов.

### Веб-интерфейс

Одна страница без сборки и внешних библиотек: форма загрузки, история
анализов, карточки сводки, SVG-графики (причины, гистограмма оценок с
порогом), таблица с поиском, фильтрами и сортировкой, кнопка выгрузки
JSON. Данные запрашиваются через `fetch`; ссылка `/#id=<id>` открывает
сохранённый результат.

## 3.4. Принципы качественного кода

- **SRP:** каждый модуль отвечает за одно — разбор, правила, признаки,
  модели, оценка, вывод, хранение; `DetectionService` только оркестрирует.
- **OCP:** новое правило — новый класс `Rule`, новая модель — новый класс
  `AnomalyModel` в `MODEL_REGISTRY`; движок и сервис не меняются.
- **LSP:** все четыре модели взаимозаменяемы в `AnomalyDetector`,
  одни и те же тесты прогоняются для каждой.
- **ISP:** интерфейс модели — 4 метода (`fit`, `score`, `get_state`,
  `from_state`), объяснение — необязательный `feature_contributions`.
- **DIP:** `DnsVerifier` получает функции reverse/forward извне (в тестах —
  поддельный резолвер), `DetectionService` — готовые verifier и модели.
- **Шаблоны:** Стратегия (правила), Фабрика (`create_model`), Фасад
  (`DetectionService`), Репозиторий (`AnalysisRepository`), Одиночка для
  загруженных моделей и соединения с БД в API (`lru_cache`).
- **PEP 8** проверяется `ruff` в CI.
